MISMO FORMATO DE TEXTO · DISTINTO CONTRATO DE SEGURIDAD
Jailbreak, inyección directa e indirecta no atacan exactamente lo mismo
Clasifícalos por quién introduce la instrucción, por dónde entra y qué control intenta superar.
01
JAILBREAKEl usuario intenta superar una restricción del modelo
usuario→petición adversarial→modelo
ENTRADApetición principal del usuario
OBJETIVO ATACADOrestricción o comportamiento de seguridad del modelo
CONTROL CLAVErobustez del modelo + evaluación adversarial
No necesita contenido externo ni RAG. Puede solaparse con técnicas de prompt injection, pero el objetivo de seguridad no es el mismo.
02
INYECCIÓN DIRECTALa entrada principal intenta cambiar la tarea de la aplicación
usuario→instrucción no autorizada→contexto
ENTRADAcanal directo de interacción
OBJETIVO ATACADOprioridad de instrucciones o tarea pretendida
CONTROL CLAVEjerarquía de instrucciones + validación del runtime
El problema aparece cuando texto con menor autoridad intenta gobernar una decisión que la aplicación reservaba a reglas superiores.
03
INYECCIÓN INDIRECTAUna fuente externa introduce instrucciones dentro de los datos
web · email · documento→retrieval / tool output→contexto
ENTRADAcontenido de terceros consultado por el sistema
OBJETIVO ATACADOfrontera entre datos no confiables y control
CONTROL CLAVEprocedencia + mínimo privilegio + autorización externa
Es prompt injection por una ruta indirecta: el atacante no necesita escribir en el chat si consigue que su contenido sea recuperado o leído.
RELACIÓNLa inyección indirecta es una ruta de prompt injection; jailbreak describe otro objetivo de seguridad.
SOLAPAMIENTOUna misma cadena de texto puede intentar ambas cosas. Clasifica el fallo por el control que debía resistirlo.
EVALUACIÓNMide por separado robustez de rechazo, resistencia a inyección y contención end-to-end antes del efecto.
