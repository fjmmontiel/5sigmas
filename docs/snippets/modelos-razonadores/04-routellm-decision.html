RouteLLM: enrutar cada query al modelo correcto
Un clasificador ligero decide qué nivel de compute necesita cada petición. Las sencillas van a modelos rápidos y baratos; solo las complejas activan el razonamiento profundo.
El router opera antes de que la query llegue al modelo de inferencia. Añade latencia mínima (~50ms) pero puede reducir el coste total en un 60-80%.

El clasificador no necesita ser perfecto — solo necesita ser bueno suficiente para que el ahorro de coste supere los errores de clasificación.
Matriz de calibración (preferido)
Se entrena usando las preferencias de un modelo fuerte (ej. GPT-4) sobre pares de respuestas. El router aprende a predecir si el modelo fuerte elegiría su propia respuesta sobre la del modelo débil.
El modelo fuerte ya sabe cuándo importa la diferencia — transferir ese conocimiento al router es barato.
Embedding de similitud
Se compara la query con queries históricas de las que se conoce el modelo óptimo. Si la query nueva es similar a las que históricamente requirieron razonamiento, se enruta al modelo fuerte.
No requiere entrenamiento supervisado — funciona con logs de producción existentes.
Clasificador supervisado directo
Un modelo pequeño (BERT, DeBERTa) entrenado con etiquetas de dificultad. Simple y fast, pero requiere etiquetar un dataset de queries de entrenamiento.
Mayor control sobre el criterio de clasificación — útil cuando el dominio es muy específico.
Umbral de enrutamiento — calibrado hacia el modelo fuerte
Rápido ⚡ ~65%
Razonador 🧠 ~35%
Error tipo I
Query simple va al razonador: coste extra, respuesta correcta
Error tipo II
Query compleja va al rápido: respuesta de menor calidad
Error tipo I (sobre-enrutar)
Query simple → modelo razonador. Coste: más dinero y latencia de lo necesario. Riesgo bajo: la respuesta es correcta.
Error tipo II (sub-enrutar)
Query compleja → modelo simple. Coste: respuesta de menor calidad. Riesgo alto: el usuario recibe una respuesta incorrecta o incompleta.
Umbral asimétrico
Los sistemas de producción calibran el umbral para minimizar los errores tipo II aunque aumenten los tipo I. El sobre-enrutamiento es caro pero seguro; el sub-enrutamiento es barato pero arriesgado.
El paper de RouteLLM (2024) reporta reducciones de coste del 85% manteniendo el 95% del rendimiento del modelo fuerte en benchmarks estándar.

El routing no es solo una optimización de infraestructura — es una decisión de producto. Implica decidir qué tipo de errores el sistema está dispuesto a aceptar y cuánto cuesta la fiabilidad adicional.
