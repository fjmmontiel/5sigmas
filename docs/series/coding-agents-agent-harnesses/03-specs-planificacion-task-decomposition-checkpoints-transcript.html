De una petición a una prueba

“Añade JSON” deja sin definir el formato y el comportamiento anterior.

El contrato concreta: --json produce un objeto válido; sin la opción se conserva el texto.

Estas condiciones permiten rechazar una implementación que sólo cumple la mitad.

Regla estable, objetivo concreto

La instrucción del repo dice cómo trabajar: no modificar la API pública sin permiso.

La spec define qué debe hacer esta tarea: añadir --json sin romper la salida existente.

Marcar una casilla del plan no cambia ninguna de esas obligaciones.

La dependencia marca el orden

Primero se acuerda el schema. Después pueden avanzar parser y serializador.

El parser ya está; falta el serializador. La prueba de extremo a extremo sigue bloqueada.

Sólo al reunir las dos piezas se habilita la prueba completa. Cerrar un subpaso no basta.

El plan puede estar equivocado

El plan supone que basta con cambiar el serializador.

La prueba revela que el parser rechaza --json antes de llegar a él.

Se revisa el plan para corregir la causa. Una hipótesis de trabajo no es evidencia de éxito.

Guardar evidencia, no sólo texto

El checkpoint conserva revisión A, tests ejecutados y decisiones pendientes.

Después cambia el parser y aparece B. Los tests dependientes quedan por repetir.

Al reanudar, se reconcilia el estado real con el checkpoint; no se hereda un PASS por proximidad.

La tarea exige el conjunto

JSON válido es una condición, no la tarea completa.

También deben conservarse la salida anterior y el alcance permitido.

Sólo la conjunción de las condiciones requeridas permite entregar; un subpaso verde no basta.
