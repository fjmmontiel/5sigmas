When retrieved context becomes a reliability risk
A RAG system can fail even when the user's request is benign if untrusted retrieved content changes how the model interprets the task.

The important security boundary is the transition from retrieved data into model decision context.

1 · NORMAL RAG

A user asks a legitimate question. The retriever selects documents and passes them to the model as supporting context.

↓
2 · CONTAMINATED CONTEXT

One retrieved document contains misleading or risk-signaling material that is not trustworthy enough to guide the agent's behavior.

↓
3 · AVAILABILITY FAILURE

The model overreacts to the retrieved context and refuses or degrades a legitimate answer even though the user's actual request is safe.

This is a reliability/security problem: safety behavior itself can become an availability failure when source trust is not represented explicitly.

Deep context analysis

Reasoning models inspect retrieved context before acting, so irrelevant or contaminated material can influence the decision process.

Weak source separation

If the system does not distinguish user intent, developer policy and retrieved data, the model receives mixed-authority context.

Large retrieval corpora

The larger and more writable the corpus, the harder it is to assume every retrieved object is trustworthy and task-relevant.

Provenance + trust labels

Preserve where each retrieved item came from and what authority it is allowed to have.

Pre-context validation

Filter and classify retrieved material before it is inserted into the model's working context.

Least-privilege corpus writes

Limit who and what can add durable content to the knowledge base, and audit changes to high-impact collections.

No single layer is sufficient. Reliable RAG combines source controls, retrieval validation, context separation and downstream monitoring.
